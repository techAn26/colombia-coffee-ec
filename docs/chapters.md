## Chapter 1: 全体像を掴もう

**ゴール**: これから作るシステムの全体像を理解し、開発環境を整える

### 学ぶ（講義パート）

#### Webサイトはどう動いているか

```
あなた（ブラウザ）  ←→  サーバー  ←→  データベース
    画面を見る         処理する        データを保存する
  （フロントエンド）  （バックエンド）      （DB）
```

- **フロントエンド**: ユーザーが見る画面。ボタンを押す、文字を入力する、画像を見る
- **バックエンド**: 裏側の処理。「この人はログインしているか？」「在庫は残っているか？」を判断する
- **データベース（DB）**: 情報の保管庫。商品情報、ユーザー情報、注文情報を保存する

#### 今回使う技術と役割

| やること | 使う技術 | 一言で |
|---------|---------|--------|
| 画面を作る | Next.js / React | Webページの「見た目」と「動き」を作るツール |
| 画面を装飾する | Tailwind CSS / shadcn/ui | デザインを効率的に当てるツール |
| データを保存する | Supabase (PostgreSQL) | データベース + 認証 + ファイル保管の統合サービス |
| 決済する | Stripe | クレジットカード決済を安全に処理するサービス |
| 公開する | Vercel | 作ったサイトをインターネットに公開するサービス |
| コードを管理する | Git / GitHub | コードの変更履歴を記録し、チームで共有する仕組み |

#### 今回作るサイトの画面構成

```
トップページ
├── 商品一覧（フィルター・検索）
│   └── 商品詳細（農園ストーリー・レビュー）
├── カート
│   └── 決済（Stripe）
│       └── 完了ページ
├── マイページ
│   ├── 注文履歴 → 注文詳細
│   ├── プロフィール編集
│   └── 配送先管理
├── ログイン（Google / LINE）
└── 管理画面（管理者のみ）
    ├── 商品管理（追加・編集・削除）
    └── 注文管理（ステータス更新）
```

## Chapter 2: データの置き場所を作ろう

**ゴール**: データベースの考え方を理解し、商品・ユーザー・注文を保存する仕組みを作る

### 学ぶ（講義パート）

#### データベースとは何か

データベースは「整理された情報の置き場所」。Excelのスプレッドシートをイメージするとわかりやすい。

```
【productsテーブル】＝ 商品一覧のExcelシートのようなもの
| id  | name                     | origin    | price |
|-----|--------------------------|-----------|-------|
| 1   | エチオピア イルガチェフェ   | エチオピア | 1200  |
| 2   | コロンビア ウィラ          | コロンビア | 1400  |
```

- **テーブル** = Excelの「シート」
- **カラム** = シートの「列」（名前、産地、価格…）
- **レコード（行）** = シートの「行」（1つ1つの商品）

#### テーブル同士の「つながり」

```
1つの商品 → 複数のバリエーション（200g, 500g, 1kg）
1人のユーザー → 複数の注文
1つの注文 → 複数の注文明細（何をいくつ買ったか）
```

これを「リレーション（関係）」と呼ぶ。1対多（1:N）の関係。

#### RLS（行レベルセキュリティ）— 「誰のデータを誰が見れるか」

```
田中さんがログイン → 田中さんの注文だけが見える
鈴木さんがログイン → 鈴木さんの注文だけが見える
管理者がログイン   → 全員の注文が見える
```

RLSは、データベースのレベルで「アクセスルール」を設定する仕組み。
アプリのコードにバグがあっても、DBが最後の砦として守ってくれる。

## Chapter 3: ログインを作ろう

**ゴール**: 「この人は誰か」を判断する仕組みを理解し、Google/LINEログインを実装する

### 学ぶ（講義パート）

#### 認証とは何か

「認証」＝「あなたは本当にあなたですか？」を確認する仕組み。

従来の方法（メール + パスワード）の問題:
- パスワードを保存する → 漏洩リスク
- パスワードを忘れる → サポート対応が大変
- セキュリティ対策（ハッシュ化、ソルト…）を自分で実装する必要がある

#### OAuthの仕組み — 「Googleに任せる」

```
① ユーザー: 「Googleでログイン」ボタンを押す
② サイト → Google: 「この人を確認してください」
③ Google → ユーザー: 「○○サイトにログインしますか？」
④ ユーザー → Google: 「はい」
⑤ Google → サイト: 「この人はtanaka@gmail.comさんです」
⑥ サイト: OKログイン完了
```

**メリット**: パスワードを自分で管理しなくていい。Google/LINEが本人確認を代行してくれる。

#### なぜLINE + Googleなのか（ビジネス判断）

- 日本人のほぼ全員がLINEかGoogleアカウントを持っている
- メール/パスワードを作る手間がなく、購入までのハードルが下がる
- パスワード管理のセキュリティリスクとサポートコストを削減

## Chapter 4: 商品を並べよう

**ゴール**: データベースの情報を画面に表示する仕組みを理解し、商品ページを作る

### 学ぶ（講義パート）

#### コンポーネント — 画面の「部品」

Reactでは画面を「部品（コンポーネント）」に分解して組み立てる。

```
商品一覧ページ
├── ヘッダー（部品）
├── フィルター（部品）
├── 商品カード（部品）× 商品の数だけ繰り返し
│   ├── 商品画像
│   ├── 商品名
│   ├── 産地
│   └── 価格
└── フッター（部品）
```

レゴブロックのように、小さな部品を組み合わせてページを作る。

#### データの流れ

```
① ページが読み込まれる
② サーバーがDBに「商品一覧をください」と問い合わせ
③ DBが商品データを返す
④ サーバーがHTMLを組み立ててブラウザに送る
⑤ ブラウザが画面を表示する
```

#### 動的ルーティング — URLで「どの商品か」が決まる

```
/products       → 商品一覧ページ
/products/abc123 → 商品ID「abc123」の詳細ページ
```

URLの一部がパラメータになっていて、それに応じて表示する商品が変わる。

#### APIを設計する

フロントエンド（画面）とバックエンド（データ）の「やりとりの約束事」を決める。

```
GET  /api/products         → 商品一覧を取得
GET  /api/products?origin=コロンビア → 産地で絞り込み
GET  /api/products/:id     → 特定の商品を取得
```

## Chapter 5: 「買う」を実現しよう

**ゴール**: カートと決済の仕組みを理解し、「商品を選んで買う」体験を完成させる

### 学ぶ（講義パート）

#### カートの仕組み

```
ユーザーが「カートに入れる」ボタンを押す
  → DBの cart_items テーブルに「誰が・何を・いくつ」を保存
  → カートページで保存されたデータを一覧表示
  → 数量変更 → DBを更新
  → 削除 → DBから削除
```

カートのデータはDBに保存するので、スマホで追加 → PCで購入も可能。

#### オンライン決済の仕組み（Stripe）

```
① カートの「購入する」ボタンを押す
② サーバーがStripeに「この内容で決済ページを作って」と依頼
③ Stripeが決済ページを生成し、ユーザーをそこにリダイレクト
④ ユーザーがカード情報を入力（※ 自分のサーバーは通らない！）
⑤ 決済完了 → StripeがWebhookで「決済OKです」と通知
⑥ サーバーが注文レコードを作成、カートをクリア
⑦ ユーザーを完了ページにリダイレクト
```

**最重要ポイント**: カード情報は**自分のサーバーを一切通らない**。
Stripeのページで処理されるから安全。もし自分でカード情報を扱うと、
PCI DSS（カード業界のセキュリティ基準）に準拠する必要があり、個人では現実的に不可能。

#### Webhookとは

「何かが起きたら知らせてくれる仕組み」。

```
Stripe: 「決済が完了しました」→ あなたのサーバーに通知（Webhook）
サーバー: 「了解、注文レコードを作成します」
```

なぜ必要か？ ユーザーが決済ページでブラウザを閉じても、
Webhookがあれば注文は確実に記録される。

## Chapter 6: 注文を届けよう

**ゴール**: 注文データの流れとステータス管理を理解し、ユーザー側・管理者側の注文管理を作る

### 学ぶ（講義パート）

#### 注文のライフサイクル

```
受注（pending）
  ↓
発送準備中（preparing）
  ↓
発送済み（shipped）
  ↓
完了（completed）

※ 受注時のみキャンセル可能（cancelled）
```

ECサイトの運用では、「今この注文はどの段階にあるか」を正確に管理することが重要。
お客さんも「自分の注文が今どうなっているか」を知りたい。

#### 管理者の権限

一般ユーザーと管理者（田中さん）では、見えるデータが違う:

| 操作 | 一般ユーザー | 管理者 |
|------|------------|--------|
| 注文を見る | 自分の注文だけ | 全ユーザーの注文 |
| ステータスを変更する | できない | できる |

**重要**: この権限チェックは**フロントエンド（画面）だけでなく、バックエンド（API/DB）でも行う**。
画面で「管理画面を非表示にする」だけでは不十分。URLを直接叩けばアクセスできてしまう。
RLSとAPIの両方でガードする。

## Chapter 7: お店を回そう

**ゴール**: 管理画面の役割を理解し、商品の追加・編集・在庫管理を作る

### 学ぶ（講義パート）

#### CRUD — データ操作の基本4パターン

ほぼすべてのWebアプリは、この4つの操作の組み合わせ:

| 操作 | 英語 | 例（商品管理） |
|------|------|--------------|
| 作る | **C**reate | 新しいコーヒー豆を登録する |
| 読む | **R**ead | 商品一覧を表示する |
| 更新 | **U**pdate | 価格や在庫数を変更する |
| 削除 | **D**elete | 販売終了した商品を削除する |

Chapter 4で作った「商品一覧・詳細」は Read。ここでは残りの Create / Update / Delete を作る。

#### ファイルストレージ — 画像の保存先

画像ファイルはDBに直接保存しない（DBが重くなる）。
代わりに:
1. 画像ファイルを「ストレージ」（ファイル置き場）にアップロード
2. DBにはそのURL（住所）だけを保存

```
商品画像 → Supabase Storage にアップロード
         → URL: https://xxx.supabase.co/storage/coffee-01.jpg
         → products テーブルの image_url カラムにURLを保存
```

#### 在庫管理の注意点

「2人が同時に最後の1個を購入しようとしたら？」
→ **楽観的ロック**（在庫チェック + 更新を1つの操作で行う）で対応。
早い者勝ちで、後から来た人には「品切れです」と表示する。

## Chapter 8: お客さんとつながろう

**ゴール**: ユーザーのプロフィール・配送先・レビューを管理する機能を作る

### 学ぶ（講義パート）

#### フォームとバリデーション

ユーザーに入力してもらう画面を「フォーム」と呼ぶ。
フォームには必ず**バリデーション（入力チェック）** が必要。

```
郵便番号: abc → NG（数字じゃない）
電話番号: 空欄 → NG（必須項目）
メール: tanaka → NG（@がない）
```

なぜ必要？
- 誤ったデータがDBに入ると後で困る
- ユーザーに「ここが間違っています」と教えてあげる優しさ

#### レビューの制約設計

「誰でもレビューできる」ようにすると、買ってもいない人がレビューを書けてしまう。
→ **購入済みチェック**: 注文履歴に該当商品があるか確認し、ある場合のみ投稿を許可。

## Chapter 9: サイトの顔を仕上げよう

**ゴール**: デザインとユーザー体験（UX）を仕上げ、プロ品質のサイトに磨き上げる

### 学ぶ（講義パート）

#### レイアウト — 全ページ共通の「枠」

```
┌──────────────────────────────┐
│  ヘッダー（ロゴ・ナビ・カート） │ ← 全ページ共通
├──────────────────────────────┤
│                              │
│  コンテンツ（ページごとに変わる）│
│                              │
├──────────────────────────────┤
│  フッター（リンク・著作権表示） │ ← 全ページ共通
└──────────────────────────────┘
```

Next.jsの `layout.tsx` に書けば、1箇所の変更で全ページに反映される。

#### レスポンシブデザイン — 画面の大きさに合わせて変わる

```
PC（横に広い）:    [商品][商品][商品][商品]  ← 4列
タブレット:         [商品][商品]              ← 2列
スマホ（縦に長い）:  [商品]                   ← 1列
```

Tailwindでは `md:grid-cols-3` のように書くだけで実現できる。
- `md:` ＝「画面幅が中くらい以上のとき」
- `grid-cols-3` ＝「3列に並べる」

#### 3つの状態 — ローディング・エラー・空

データを取得する画面には、必ず3つの状態がある:

| 状態 | いつ起きるか | 表示すべきもの |
|------|------------|-------------|
| ローディング | データ取得中 | スピナーや骨格UI |
| エラー | 取得失敗 | 「問題が発生しました」メッセージ |
| 空 | データが0件 | 「まだ商品がありません」メッセージ |

何も表示しないと、ユーザーは「壊れてる？」と不安になる。

## Chapter 10: 品質を確かめよう

**ゴール**: テストの考え方を理解し、サイトが「ちゃんと動く」ことを証明する

### 学ぶ（講義パート）

#### テストの種類

| 種類 | 何をするか | 例 |
|------|----------|-----|
| 手動テスト | 自分でサイトを操作して確認 | 「商品を検索して買ってみる」 |
| ユニットテスト | コードの一部分を自動で確認 | 「合計金額の計算が正しいか」 |
| E2Eテスト | ユーザーの操作を丸ごと自動で再現 | 「ログイン→商品選択→決済」を自動実行 |

#### なぜテストが必要か

「自分で触って動いたからOK」だと不十分な理由:
- **見落とし**: 100通りの操作パターンを毎回手動で確認するのは現実的でない
- **退行（リグレッション）**: Aを直したらBが壊れた、に気づけない
- **信頼の証明**: 「テストが通っています」は品質の証拠になる

#### デプロイとは

「デプロイ」＝ 作ったサイトを公開すること。

今まで: `localhost:3000`（自分のPCだけで見えていた）
デプロイ後: `https://colombia-coffee.vercel.app`（世界中から見える）

#### テスト環境と本番環境

| | テスト環境 | 本番環境 |
|--|----------|---------|
| 目的 | 開発・動作確認用 | 実際のユーザーが使う |
| Stripe | テストモード（お金は動かない） | 本番モード（実際に決済） |
| データ | ダミーデータ | 実際の商品データ |
| URL | localhost:3000 | https://your-domain.com |

テスト用の鍵を本番で使うと決済が動かない。本番の鍵をコードに書くとセキュリティ事故になる。
→ だから「環境変数」で切り替える。

#### OGP — SNSでシェアされたときの「見た目」

TwitterやLINEでURLを送ると、タイトル・説明・画像が表示される。あれがOGP。
設定しないと「無題のページ」のように表示されてしまい、もったいない。

「リリースして終わり」ではない。むしろ、**使い始めてから見えてくること**の方が多い。

```

【学び】 何を得たか、次にどう活かすか
```

この構造で語れることが、「AIで作っただけの人」と「自分のプロダクトとして理解している人」の違い。
