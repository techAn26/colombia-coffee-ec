## Step 1-1: Next.js + TypeScript プロジェクト初期化

### 何のためにやったのか

Webサイトを作るには「開発環境」が必要。
料理に例えると、これは**キッチンと調理器具を揃える**作業にあたる。

### 何をしたのか

`create-next-app` というコマンドを使って、Next.jsプロジェクトを自動生成した。

```bash
npx create-next-app@latest . --typescript --tailwind --eslint --app --src-dir
```

このコマンド1つで、以下のものが自動で用意される:

| 生成されたもの | 何のためにあるか |
|--------------|----------------|
| `src/app/` フォルダ | ここにページ（画面）を作っていく場所 |
| `src/app/page.tsx` | トップページの中身 |
| `src/app/layout.tsx` | 全ページ共通の「枠」（ヘッダー・フッターなど） |
| `package.json` | プロジェクトが使う道具（ライブラリ）の一覧表 |
| `tsconfig.json` | TypeScriptの設定ファイル |
| `node_modules/` | 実際にインストールされた道具の中身（大量のファイル） |

### ここで理解しておくべきこと

#### フロントエンド・バックエンド・データベースの役割

```
あなた（ブラウザ）  ←→  サーバー  ←→  データベース
    画面を見る         処理する        データを保存する
  （フロントエンド）  （バックエンド）      （DB）
```

- **フロントエンド**: ブラウザに表示される「見た目」の部分。ボタン、画像、テキストなど
- **バックエンド**: 裏側で動く「処理」の部分。「ログインしているか？」「在庫はあるか？」を判断する
- **データベース（DB）**: 情報の保管庫。商品、ユーザー、注文のデータを保存する

Next.jsはこの**フロントエンドとバックエンドの両方を1つで担当できる**フレームワーク。
だから今回の開発に適している。

#### TypeScriptとは

JavaScriptに「型」をつけたもの。

```typescript
// JavaScriptだと、何でも入れられる（危険）
let price = 1200;
price = "千二百円"; // エラーにならない → バグの原因になる

// TypeScriptだと、型が合わないとエラーになる（安全）
let price: number = 1200;
price = "千二百円"; // エラー！ → バグを未然に防げる
```

「数字の場所に文字を入れてしまった」のようなミスを、**コードを書いた時点で検出してくれる**。

#### `npm run dev` で開発サーバーが起動する

開発中は自分のPC上で「仮のサーバー」を動かして動作確認する。

```bash
npm run dev
# → http://localhost:3000 でブラウザからアクセスできる
```

`localhost` = 「自分のPC」という意味。この段階では**自分のPCだけで見えている**。
外部に公開するのは、Chapter 11（リリース）で行う。

### 確認したこと

- [x] `npx tsc --noEmit` で型エラーがないことを確認
- [x] `npm run dev` で開発サーバーが起動し、ブラウザでページが表示されることを確認

## Step 1-2: Tailwind CSS + shadcn/ui セットアップ

### 何のためにやったのか

Webサイトの「見た目」を効率的に作るためのツールを導入した。
料理に例えると、**調味料と便利な調理キットを揃える**作業。

### 何をしたのか

#### 1. shadcn/ui を初期化

```bash
npx shadcn@latest init -d
```

これにより、以下が追加された:

| 追加されたもの | 何のためにあるか |
|--------------|----------------|
| `components.json` | shadcn/uiの設定ファイル |
| `src/components/ui/button.tsx` | ボタン部品（最初のUIコンポーネント） |
| `src/lib/utils.ts` | CSSクラスを結合するユーティリティ関数 |

#### 2. コーヒーECサイト用のテーマカラーを設定

`src/app/globals.css` のカラー変数を、コロンビアコーヒーをイメージした**温かみのあるブラウン系**に変更した。

| 色の役割 | 変更前 | 変更後 | イメージ |
|---------|--------|--------|---------|
| primary（メインカラー） | 黒 | ダークブラウン | コーヒー豆の色 |
| background（背景色） | 白 | ほんのり暖かいクリーム色 | カフェの雰囲気 |
| accent（アクセントカラー） | グレー | ミディアムブラウン | 焙煎した豆の色 |

#### 3. トップページを仮の内容に置き換え

Next.jsのデフォルトのWelcomeページを、コーヒーECサイトの仮トップページに置き換えた。

```
「コロンビアから届く、農園の想いが詰まった一杯。」
```

というキャッチコピーと、ヘッダー・フッターを配置。

### ここで理解しておくべきこと

#### Tailwind CSSとは

HTMLに直接スタイルを書く仕組み。従来のCSSと比べてみると:

```html
<!-- 従来のCSS：別ファイルにスタイルを書く -->
<p class="title">こんにちは</p>

<!-- styles.css -->
.title { color: red; font-size: 24px; font-weight: bold; }

<!-- Tailwind CSS：HTMLに直接書く -->
<p class="text-red-500 text-2xl font-bold">こんにちは</p>
```

Tailwindでは `text-red-500`（赤い文字）、`text-2xl`（大きめの文字）のように、
**意味がわかりやすい名前のクラス**を組み合わせてスタイルを当てる。

#### shadcn/uiとは

ボタン、フォーム、モーダルなどの**よく使うUI部品（コンポーネント）のコレクション**。

```tsx
// shadcn/uiのButtonを使う
import { Button } from "@/components/ui/button";

<Button variant="outline" size="sm">ログイン</Button>
```

自分でボタンのデザインを一から作る必要がなく、**プロ品質のUI部品をすぐに使える**。

### 確認したこと

- [x] `npx tsc --noEmit` で型エラーがないことを確認
- [x] shadcn/uiのButtonコンポーネントが正しく読み込まれることを確認

## Step 1-3: Git リポジトリ初期化・.gitignore整備

### 何のためにやったのか

コードの**変更履歴を管理する仕組み**を整え、
**公開してはいけないファイル（APIキーなど）をGitに入れないように設定**した。

### 何をしたのか

#### 1. Git リポジトリの確認

`create-next-app` がgit initと初回コミットを自動で行っていた。

#### 2. .gitignoreの確認・整備

`.gitignore` は「Gitで管理しないファイル」を指定するファイル。

以下が正しくignoreされていることを確認:

| ファイル | ignoreする理由 |
|---------|---------------|
| `.env*`（環境変数ファイル） | APIキーやパスワードなどの機密情報が含まれるため |
| `node_modules/` | サイズが巨大（数百MB）で、`npm install` で再生成できるため |
| `.next/` | ビルド生成物で、再生成できるため |

#### 3. 環境変数テンプレートの作成

`.env.local.example` というテンプレートファイルを作成した。

```
# Supabase
NEXT_PUBLIC_SUPABASE_URL=your-supabase-url
NEXT_PUBLIC_SUPABASE_ANON_KEY=your-supabase-anon-key

# Stripe
STRIPE_SECRET_KEY=sk_test_xxx
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_xxx
STRIPE_WEBHOOK_SECRET=whsec_xxx
```

**なぜテンプレートが必要か？**
- `.env.local`（実際のキーが入ったファイル）はGitに入れない
- でも「どんな環境変数が必要か」は他の開発者にも知らせたい
- だから**値をダミーにしたテンプレート**だけGitに入れる

### ここで理解しておくべきこと

#### Gitとは

コードの**セーブポイント（コミット）を記録する仕組み**。

```
コミット1: プロジェクト作成
  ↓
コミット2: デザインツール導入
  ↓
コミット3: .gitignore整備
  ↓
コミット4: 画面設計ドキュメント追加
```

ゲームのセーブデータのように、**いつでも過去の状態に戻れる**。
「さっきの変更で壊れた！」というときに、前のコミットに戻せばOK。

#### 環境変数とは

アプリの**設定値を外部から渡す仕組み**。
コードの中に直接書くと危険な「鍵」を、安全に管理するために使う。

```
コードに書く場合（NG）:
  const key = "sk_live_abc123xyz";  // ← GitHubに公開されたら大惨事

環境変数を使う場合（OK）:
  const key = process.env.STRIPE_SECRET_KEY;  // ← 値は.envファイルから読み込む
```

`.env.local` ファイルは `.gitignore` でGitから除外されるため、
GitHubに公開されても鍵が漏れる心配がない。

### 確認したこと

- [x] `.env`, `.env.local`, `.env.production` がすべてgitignoreされていることを確認
- [x] `.env.local.example`（テンプレート）はignoreされないことを確認

## Step 1-4: 画面一覧・画面遷移の整理

### 何のためにやったのか

実装に入る前に、**サイト全体の画面構成**を整理した。
家を建てる前に**間取り図を描く**のと同じ。

何も考えずにコードを書き始めると、後から「あ、この画面忘れてた」「ここからどう遷移するんだっけ」となる。

### 何をしたのか

`docs/screen-design.md` に以下を整理した:

#### 1. 全16画面の一覧

| 区分 | 画面数 | 例 |
|------|-------|-----|
| 公開ページ（誰でも見える） | 3画面 | トップ、商品一覧、商品詳細 |
| 認証ページ | 1画面 | ログイン |
| 会員専用ページ | 7画面 | カート、注文履歴、プロフィール等 |
| 管理者ページ | 5画面 | 商品管理、注文管理等 |

#### 2. 画面遷移図（3つのフロー）

- **メインフロー**: トップ → 商品一覧 → 商品詳細 → カート → 決済 → 完了
- **マイページフロー**: マイページ → 注文履歴/プロフィール/配送先
- **管理者フロー**: 管理ダッシュボード → 商品管理/注文管理

#### 3. 認証ガード（アクセス制御）

| ページ | 誰がアクセスできるか |
|--------|-------------------|
| トップ、商品一覧/詳細 | 誰でも（ログイン不要） |
| カート、マイページ | ログインしたユーザーのみ |
| 管理画面 | 管理者（admin）のみ |

#### 4. レスポンシブ設計

スマホ→タブレット→PCで商品グリッドの列数が変わる設計。

### ここで理解しておくべきこと

#### URLのパス設計

```
/products        → 商品一覧
/products/abc123 → 商品ID「abc123」の詳細ページ
/mypage/orders   → 注文履歴
/admin/products  → 管理者の商品管理
```

URLのパスは、サイトの「住所」のようなもの。
`/admin/` で始まるページは管理者用、`/mypage/` で始まるページは会員用、
のように**パスの構造でアクセス権限がわかる**ように設計した。

#### Next.jsのApp Routerとフォルダ構造

Next.jsでは、**フォルダ構造がそのままURLのパスになる**:

```
src/app/
  page.tsx                    → /
  products/
    page.tsx                  → /products
    [id]/
      page.tsx                → /products/[id]  ← [id]は動的パラメータ
  mypage/
    page.tsx                  → /mypage
    orders/
      page.tsx                → /mypage/orders
  admin/
    page.tsx                  → /admin
```

`[id]` の部分は「動的ルーティング」と呼ばれ、URLのその部分が変数になる。
`/products/abc123` にアクセスすると、`id = "abc123"` として使える。

- [x] 全16画面に抜け漏れがないことを確認
- [x] 画面遷移に矛盾がないことを確認（行き止まりがない）
- [x] 認証ガードの設定が適切であることを確認

### Step 1-3 の学習プロセス: Git・環境変数

#### INPUT: AIへの質問（理解フェーズ）

> **田中**: .envファイルをGitHubに上げちゃったらどうなるの？
>
