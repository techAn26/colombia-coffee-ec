# Chapter 2: データの置き場所を作ろう — 開発記録

実施日: 2026-05-14

---

## このChapterで何をしたのか（概要）

コーヒーECサイトのデータを保存する「場所」を設計・構築した。
具体的には、以下の3つのことを行った:

1. **DB設計を最終確認・更新した**（Step 2-1）
2. **Supabaseプロジェクトを作成し、アプリと接続した**（Step 2-2）
3. **テーブル・RLSポリシー・インデックスを実際に作成した**（Step 2-3）

---

## Step 2-1: DB詳細設計の最終確認・更新

### 何のためにやったのか

前回作成したDB設計書（db-design.md）を実装前に最終チェックした。
設計段階で漏れていたカラムがあれば、後から追加するよりも**今のうちに直す**方が圧倒的に楽。

### 何をしたのか

productsテーブルにスペシャリティコーヒーとして重要な2カラムを追加:
- `process`（精製方法）: washed / natural / honey など
- `altitude`（標高）: 1,600-1,900m など

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: テーブル設計ってもう完成だと思ってたんだけど、まだ変わるの？
>
> **AI**: 設計は「仮」でいいと言いましたが、実装前に一度見直すことは大事です。
> 今回の場合、スペシャリティコーヒーの商品情報として「精製方法」と「標高」が
> 抜けていました。これらはコーヒーの味に大きく影響する情報で、
> お客さんが豆を選ぶときに重要な判断基準になります。
>
> **田中**: 確かに、農園を訪れたときも精製方法の話はよく出たな。
> ウォッシュドとナチュラルで全然味が違うし。
>
> **AI**: そうですね。後からカラムを追加することもできますが、
> 最初に入れておく方が、マイグレーションの管理がシンプルになります。

#### OUTPUT: 田中さんの理解

> **田中のメモ**:
> - DB設計は最初から完璧じゃなくていい。でも実装前に「漏れ」がないか見直すのは大事
> - 後からカラム追加もできるが、最初に入れておく方が楽
> - 仕様変更があったら `docs/records/spec-changes.md` に記録する → v1完成時に仕様書をfixするため

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | productsテーブルにprocess（精製方法）とaltitude（標高）を追加した |
| **Why** | スペシャリティコーヒーでは精製方法・標高が味の重要な決定要因。お客さんの豆選びに必要 |

## Step 2-2: Supabase プロジェクト作成・接続設定

### 何のためにやったのか

設計したデータベースを実際に動かすために、**Supabase**というサービスにプロジェクトを作り、
アプリ（Next.js）と接続できるようにした。

料理に例えると、**冷蔵庫（データの保管場所）を購入して、キッチンに設置した**ような作業。

### 何をしたのか

#### 1. Supabaseプロジェクト作成

| 項目 | 内容 |
|------|------|
| プロジェクト名 | colombia-coffee |
| リージョン | ap-northeast-1（東京） |
| コスト | $0/月（無料プラン） |

#### 2. 必要なパッケージをインストール

```bash
npm install @supabase/supabase-js @supabase/ssr
```

- `@supabase/supabase-js`: Supabaseと通信するためのライブラリ
- `@supabase/ssr`: Next.jsのサーバーサイドレンダリングでSupabaseを使うためのライブラリ

#### 3. 接続設定ファイルを作成

3つのファイルを作成:

| ファイル | 用途 |
|---------|------|
| `src/lib/supabase/server.ts` | サーバーコンポーネント用のSupabaseクライアント |
| `src/lib/supabase/client.ts` | クライアントコンポーネント用のSupabaseクライアント |
| `src/middleware.ts` | セッション（ログイン状態）を自動で更新するミドルウェア |

#### 4. 環境変数を設定

`.env.local` にSupabaseの接続情報（URLとAPIキー）を設定した。
このファイルは `.gitignore` で除外されているため、GitHubに公開されない。

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: サーバー用とクライアント用で2つのファイルを作るのはなぜ？1つじゃダメ？
>
> **AI**: Next.jsでは、画面の描画が「サーバー」と「ブラウザ」の2箇所で行われます。
>
> - **サーバーコンポーネント**: サーバー上で実行される。DBに直接アクセスできる。
>   セキュリティ的にも安全（ユーザーにコードが見えない）
> - **クライアントコンポーネント**: ブラウザ上で実行される。ボタンクリックなどの
>   インタラクションを処理する
>
> それぞれ環境が違うので、Cookieの扱い方が異なります。
> サーバー側は `next/headers` からCookieを読み取り、
> クライアント側はブラウザのCookieを使います。
>
> **田中**: ミドルウェアって何？
>
> **AI**: 「すべてのページアクセスの前に実行される処理」です。
> 今回の場合、ユーザーがどのページにアクセスしても、
> 自動でログインセッションを更新（リフレッシュ）します。
> これがないと、一定時間経つとログイン状態が切れてしまいます。
>
> **田中**: ドアの前にいる警備員みたいなもの？
>
> **AI**: まさにそのイメージです！全ての訪問者のIDカード（セッション）を
> チェックして、有効期限が切れそうなら更新してくれる警備員です。

#### OUTPUT: 田中さんの理解

> **田中のメモ**:
> - Supabase = データベース + 認証 + ファイル保管が一体になったサービス
> - サーバー用とクライアント用でクライアントを分ける理由: 実行環境（サーバー/ブラウザ）が違うからCookieの扱い方が異なる
> - ミドルウェア = 「全ページの前に実行される処理」。ログインセッションの自動更新をしてくれる「警備員」
> - `.env.local` に接続情報を保存。このファイルはGitに入らない（セキュリティ）

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | Supabaseプロジェクトを作成し、Next.jsアプリと接続した。サーバー用/クライアント用のクライアント設定とミドルウェアを作成した |
| **Why** | データを保存・取得するために、アプリとデータベースをつなぐ必要がある |
| **How** | 環境変数（.env.local）にSupabaseのURL・APIキーを設定し、それを読み込むクライアントファイルを作成した。ミドルウェアがセッションを自動更新する |
| **If** | 環境変数が間違っていたらDBに接続できず、商品一覧も表示されない。ミドルウェアがなければログイン状態が維持できない |
| **Next** | Stripe決済を追加するときは、Stripeの環境変数もここに追加する |

## Step 2-3: DBマイグレーション（テーブル・RLS作成）

### 何のためにやったのか

設計書（db-design.md）に書いた内容を、**実際のデータベースに作成**した。
設計図を見ながら、実際に家を建てる作業にあたる。

### 何をしたのか

#### 1. マイグレーションSQLを作成・実行

2つのマイグレーションファイルを作成し、Supabase上で実行:

| ファイル | 内容 |
|---------|------|
| `20260514_001_initial_schema.sql` | テーブル9個、インデックス10個、トリガー9個、初期データ1件 |
| `20260514_002_rls_policies.sql` | RLSポリシー25個、ヘルパー関数1個 |

#### 2. 作成されたテーブル一覧

| テーブル | RLS | 初期データ | 用途 |
|---------|-----|----------|------|
| profiles | 有効 | 0件 | ユーザー情報 |
| categories | 有効 | 1件（コーヒー豆） | カテゴリ |
| products | 有効 | 0件 | 商品情報 |
| product_variants | 有効 | 0件 | 商品バリエーション（重量・価格） |
| cart_items | 有効 | 0件 | カート |
| orders | 有効 | 0件 | 注文 |
| order_items | 有効 | 0件 | 注文明細 |
| reviews | 有効 | 0件 | レビュー |
| shipping_addresses | 有効 | 0件 | 配送先 |

#### 3. 自動化された仕組み（トリガー）

| トリガー | 何をするか |
|---------|----------|
| `on_auth_user_created` | ユーザーがサインアップしたら、自動でprofilesテーブルにレコードを作成。名前とアバターURLをOAuth情報から取得 |
| `set_updated_at`（7テーブル） | レコードが更新されたら、自動で `updated_at` を現在時刻に更新 |

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: マイグレーションファイルって何？直接ダッシュボードでテーブル作っちゃダメ？
>
> **AI**: ダメではないですが、マイグレーションファイルがある方が安全です。
> マイグレーションファイルは「DBの変更履歴」です。Gitでいうコミットのようなもの。
>
> メリット:
> 1. **再現性**: 同じSQLを実行すれば、別の環境でも同じDBを再現できる
> 2. **追跡性**: いつ、何を変更したか記録が残る
> 3. **チーム開発**: 鈴木さんも同じDBをローカルに作れる
>
> ダッシュボードで手動で作ると、「何をどう作ったか」の記録が残りません。
>
> **田中**: なるほど、レシピを書き残すようなものか。レシピがあれば誰でも同じ料理が作れる
>
> **AI**: その通りです！
>
> **田中**: RLSのポリシーが25個もあるけど、全部必要なの？
>
> **AI**: はい。各テーブルに対して「誰が」「何をできるか」を4つの操作
> （SELECT/INSERT/UPDATE/DELETE）ごとに定義しています。
> 例えば cart_items テーブルだけで4つ:
> - SELECT: 自分のカートだけ見える
> - INSERT: 自分のカートにだけ追加できる
> - UPDATE: 自分のカートだけ変更できる
> - DELETE: 自分のカートからだけ削除できる
>
> もしRLSがなかったら、Aさんのカートの中身がBさんに見えてしまいます。
>
> **田中**: それは怖い…。25個全部ちゃんと設定するの大事だね

#### OUTPUT: 田中さんの理解

> **田中のメモ**:
> - マイグレーション = DBの変更履歴。レシピのようなもの。これがあれば同じDBを再現できる
> - SQLは「データベースと話すための言語」。`CREATE TABLE` でテーブルを作る、`INSERT` でデータを入れる
> - RLS = 行レベルセキュリティ。テーブルごとに「誰が何をできるか」を定義するルール
> - RLSがなかったら、他のユーザーのカートや注文が丸見えになる → セキュリティの最後の砦
> - トリガー = 「何かが起きたら自動で別の処理をする」仕組み。ユーザー登録したら自動でプロフィール作成、更新したら自動でupdated_at更新
> - `is_admin()` というヘルパー関数で「この人は管理者か？」を簡単にチェックできるようにした

#### 鈴木さん（友人エンジニア）のレビュー

> **鈴木**: マイグレーション見たよ。いくつか確認。
>
> **鈴木**: profilesのUPDATEポリシーで `role = (select role from profiles where id = auth.uid())` としてるのは、ユーザーが自分のroleを変更できないようにするためだね？
>
> **田中**: そう、AIが「管理者権限の昇格を防ぐため」って言ってた。
>
> **鈴木**: 正解。これがないと、誰でもDevToolsからAPIを叩いて自分をadminにできちゃう。
> ordersのINSERTにRLSポリシーがないのも意図的だね？
>
> **田中**: うん、注文の作成はStripe Webhookからサーバー側でやるから、フロントからは直接作れないようにしてる。
>
> **鈴木**: OK、ちゃんとわかってるね。RLSの設計は問題なさそう。

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | 9つのテーブル、10のインデックス、25のRLSポリシー、9つのトリガーをDBに作成した |
| **Why** | 設計書に書いた「どんなデータを保存するか」「誰がアクセスできるか」を実際にDBに反映するため |
| **How** | SQLでテーブルを定義し、マイグレーションファイルとしてSupabaseに適用。RLSで行単位のアクセス制御を設定 |
| **If** | RLSがなければ全ユーザーのデータが丸見え。トリガーがなければprofilesの自動作成やupdated_atの自動更新が動かない |
| **Next** | 次のChapter（認証）でユーザーが実際にログインすると、profilesテーブルに自動でレコードが作られる |

### 田中さんの学びまとめ

| 学んだ概念 | 田中さんの理解（自分の言葉で） |
|----------|--------------------------|
| データベース | 「整理された情報の置き場所」。Excelのシートのようなもの |
| テーブル | Excelの1つのシート。商品、ユーザー、注文ごとに分けて管理 |
| リレーション | テーブル同士のつながり。1つの商品→複数のバリエーション、1人のユーザー→複数の注文 |
| RLS | 行レベルセキュリティ。「自分のデータだけ見える」ルールをDBのレベルで強制する仕組み |
| マイグレーション | DBの変更履歴。レシピのようなもの。これがあれば同じDBを再現できる |
| トリガー | 「何かが起きたら自動で別の処理をする」仕組み |
| ミドルウェア | 全ページの前に実行される処理。ログインセッションを自動更新する「警備員」 |
| 環境変数 | APIキーなどの機密情報をコードの外で安全に管理する仕組み |
