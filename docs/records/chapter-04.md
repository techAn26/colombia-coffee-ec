## Step 4-0: API設計

### 何のためにやったのか

フロントエンド（画面）とバックエンド（データ）がどうやりとりするか、事前に整理した。

### 何をしたのか

**重要な設計判断**: Next.js App Routerでは、サーバーコンポーネントから直接Supabaseにクエリできるため、商品取得のためにわざわざAPI Routeを作る必要がない。

| データ操作 | 方式 | 理由 |
|----------|------|------|
| データ取得（GET系） | サーバーコンポーネントで直接 | API Routeを経由する無駄を省く |
| データ変更（POST/PATCH/DELETE） | Server Action | フォーム送信やボタン操作と自然に統合 |
| 外部サービス連携 | API Route | Stripe Webhookなど、Next.jsの外から呼ばれるもの |

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: API設計って、全部のデータ取得にAPIエンドポイントが必要じゃないの？
>
> **AI**: 従来のWebアプリではそうでした。でもNext.jsのApp Routerでは、
> サーバーコンポーネントが直接データベースにアクセスできるので、
> 「画面→APIエンドポイント→データベース」ではなく
> 「画面（サーバーで実行）→データベース」と直接つながります。
>
> APIエンドポイントを挟むのは、余計な中継地点を作るようなもの。
> 産地直送できるのに、わざわざ卸売業者を通す必要はないですよね。
>
> **田中**: じゃあAPIエンドポイントはいつ使うの？
>
> **AI**: 外部からNext.jsの中に通知が来るとき、です。
> 例えばStripeが「決済完了しました」と教えてくれるWebhookは、
> Stripeのサーバーから直接アクセスされるので、APIエンドポイントが必要です。
>
> **田中**: なるほど、産地直送できるものは直送、外部からの荷物は受付窓口（API）が必要、か

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | API設計ドキュメントを作成し、サーバーコンポーネント直接/Server Action/API Routeの使い分けを整理した |
| **Why** | 「どの方式でデータを取得・変更するか」を事前に決めておかないと、実装がバラバラになる |

## Step 4-1: デモデータ投入 + 商品一覧ページ

### 何のためにやったのか

実際の画面を作るには、表示するデータが必要。コロンビアのコーヒー豆5種類のデモデータを投入し、それを一覧表示するページを作成した。

### 何をしたのか

#### デモデータ（5種類のコーヒー豆）

| 商品名 | 産地 | 焙煎度 | 精製方法 | 200g価格 |
|--------|------|--------|---------|---------|
| ウィラ エル・パライソ農園 | ウィラ県 | 中煎り | ダブルアナエロビック | ¥1,800 |
| ナリーニョ ラ・エスメラルダ農園 | ナリーニョ県 | 浅煎り | ウォッシュド | ¥1,600 |
| ウィラ サン・アグスティン | ウィラ県 | 中煎り | ナチュラル | ¥1,500 |
| カウカ ポパヤン | カウカ県 | 深煎り | ハニー | ¥1,400 |
| シエラネバダ デカフェ | マグダレナ県 | 中煎り | ウォッシュド（デカフェ） | ¥1,700 |

各商品に200g / 500g / 1kgの3バリエーション（計15バリエーション）。

#### 商品一覧ページの構成

- サーバーコンポーネントでSupabaseから商品データを直接取得
- レスポンシブグリッド: スマホ1列 → sm 2列 → lg 3列 → xl 4列
- 商品カード: 画像（仮）、商品名、焙煎度バッジ、産地、フレーバー、最低価格

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: 「コンポーネント」って結局何なの？
>
> **AI**: 画面の「部品」です。レゴブロックだと思ってください。
>
> ```
> 商品一覧ページ（完成品）
>   = ヘッダー（部品） + フィルター（部品） + 商品カード（部品）× 5 + フッター（部品）
> ```
>
> 商品カードという部品を1つ作れば、それを5回繰り返して5商品分表示できます。
> 部品を変更すれば、全ての商品カードに反映されます。
>
> **田中**: レゴなら分かる！同じブロックを何個も使い回すんだな
>
> **田中**: データはどこから来るの？
>
> **AI**: 流れはこうです:
>
> ```
> ① ユーザーが /products にアクセス
> ② サーバー上で page.tsx が実行される
> ③ page.tsx 内の getProducts() が Supabase にクエリを投げる
> ④ Supabase が PostgreSQL から商品データを返す
> ⑤ サーバーが HTML を組み立ててブラウザに送る
> ⑥ ブラウザが商品一覧を表示する
> ```
>
> これがサーバーコンポーネントの強み。データ取得がサーバー上で完結するので、
> APIキーがブラウザに露出しません。

#### OUTPUT: 田中さんの理解

> **田中のメモ**:
> - コンポーネント = レゴブロック。1つ作って使い回す
> - サーバーコンポーネントではデータ取得がサーバー上で完結する
> - `getProducts()` → Supabase → PostgreSQL → データが返ってくる
> - 商品カードに「¥1,400〜」と最低価格を表示。product_variantsの中で一番安い価格

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | デモデータ5商品を投入し、商品一覧ページを作成した |
| **Why** | 画面を作るにはデータが必要。実際のコーヒー豆データで動作確認する |
| **How** | サーバーコンポーネントからSupabaseに直接クエリし、結果をグリッド表示 |
| **If** | データが0件なら「該当する商品が見つかりませんでした」と表示される |

## Step 4-2 & 4-3: フィルター＋キーワード検索

### 何のためにやったのか

お客さんが「浅煎りのコーヒーだけ見たい」「チョコレート系のフレーバーで探したい」というときに絞り込めるようにした。

### 何をしたのか

3つのフィルター + キーワード検索:

| フィルター | 操作 | URL |
|----------|------|-----|
| 産地 | セレクトボックス | `?origin=コロンビア ウィラ県` |
| 焙煎度 | セレクトボックス | `?roast=light` |
| フレーバー | セレクトボックス | `?flavor=チョコレート` |
| キーワード検索 | テキスト入力 | `?q=エチオピア` |

**重要な設計判断**: フィルター状態をURLのsearchParamsで管理。

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: フィルターの状態をURLに入れるのはなぜ？画面の中で覚えておけばいいんじゃない？
>
> **AI**: URLにフィルター状態を持たせると、3つメリットがあります:
>
> 1. **共有できる**: 「浅煎りのコーヒー一覧」のURLをLINEで送れる
> 2. **ブックマークできる**: お気に入りの検索条件を保存できる
> 3. **戻るボタンが効く**: ブラウザの戻るで前のフィルター状態に戻れる
>
> 画面の中だけで覚えると（React state）、ページを離れたら消えてしまいます。
>
> **田中**: 確かに、「この検索結果見て」ってURLを送れるの便利だな。Amazonもそうなってるし

#### 判断の記録

| 判断ポイント | 田中さんの判断 | 理由 |
|------------|--------------|------|
| フィルターのUI形式 | セレクトボックス | 選択肢が少ないので、チェックボックスよりシンプル |
| フレーバーフィルタの実装 | アプリ側フィルター | PostgreSQLの配列フィルターは複雑なため |
| 検索のdebounce | 300ms | 入力のたびにクエリを飛ばさないように |

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | 3つのフィルターとキーワード検索を実装した |
| **Why** | お客さんが自分の好みでコーヒー豆を絞り込めるようにするため |
| **How** | フィルター操作→URLのsearchParamsを更新→サーバーでクエリ実行→結果を再表示 |

## Step 4-4: 商品詳細ページ

### 何のためにやったのか

商品一覧から1つの商品をクリックしたときに、詳しい情報を見せるページを作った。

### 何をしたのか

`/products/[id]` の動的ルーティングで商品詳細ページを作成:

- 商品画像（仮のプレースホルダー）
- スペック一覧（産地、農園、焙煎度、精製方法、標高）
- フレーバーノート（バッジ表示）
- バリエーション一覧（200g / 500g / 1kg + 価格 + 在庫状況）
- カートに入れるボタン（Chapter 5で実装予定）
- 農園ストーリー（全文表示）
- レビューセクション（Chapter 8で実装予定）

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: `[id]` って何？フォルダ名に角括弧って変じゃない？
>
> **AI**: Next.jsの「動的ルーティング」です。`[id]` はパラメータの名前で、
> URLの一部が変数になります。
>
> ```
> /products/abc123  →  id = "abc123"
> /products/xyz789  →  id = "xyz789"
> ```
>
> つまり、1つの `page.tsx` ファイルで、全ての商品の詳細ページを表示できます。
> 商品が100個あっても、ファイルは1つだけ。
>
> **田中**: 住所の「○○番地」みたいなもの？同じ「家の間取り（テンプレート）」で、
> 住所（id）が違えば別の家（商品）が表示される
>
> **AI**: はい、まさにそのイメージです。

#### OUTPUT: 田中さんの理解

> **田中のメモ**:
> - 動的ルーティング = URLの一部を変数にする仕組み。`[id]` フォルダで実現
> - `notFound()` = 該当する商品がなかったら404ページを表示する関数
> - バリエーション表示: sort_orderで並び替えて、200g→500g→1kgの順に表示
> - 在庫5以下は「残りN点」と表示、0は「品切れ」
> - 農園ストーリーは商品情報の下に全文表示。田中さんの強みであるストーリーを最大限見せる

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | 商品詳細ページを作成。スペック、バリエーション、農園ストーリーを表示 |
| **Why** | お客さんが購入前に詳しい情報（産地、精製方法、農園の想い）を確認するため |
| **How** | 動的ルーティング `/products/[id]` でURLのidから商品を特定し、Supabaseから取得して表示 |
| **If** | 存在しないidにアクセスしたら404ページが表示される（`notFound()`） |
| **Next** | カートに入れるボタンはChapter 5、レビューはChapter 8で本実装 |

### 田中さんの学びまとめ

| 学んだ概念 | 田中さんの理解（自分の言葉で） |
|----------|--------------------------|
| コンポーネント | レゴブロック。1つ作って何回も使い回せる画面の部品 |
| サーバーコンポーネント | サーバー上で実行される部品。データ取得がサーバーで完結するのでAPIキーが漏れない |
| 動的ルーティング | URLの一部を変数にする仕組み。`[id]`で全商品を1つのファイルで表示 |
| searchParams | URLのパラメータ。フィルター状態をURLに持たせることで共有・ブックマークが可能 |
| Server Action | サーバー上で実行される関数。フォーム送信やボタン操作でデータを変更する |
