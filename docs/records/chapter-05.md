### 何のためにやったのか

オンライン決済を処理するために、Stripe の SDK と初期化設定を準備した。

### 何をしたのか

1. `stripe` パッケージをインストール
2. `src/lib/stripe.ts` — Stripe 初期化ユーティリティ
3. `src/lib/supabase/admin.ts` — service_role key を使う管理者用 Supabase クライアント（Webhook 用）

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: service_role key って何？anon key と何が違うの？
>
> **AI**: 鍵の「権限の強さ」が違います。
>
> | キー | 権限 | 用途 |
> |------|------|------|
> | anon key | RLS に従う（制限あり） | 通常のユーザー操作 |
> | service_role key | RLS をバイパス（全権限） | サーバー側の管理操作 |
>
> anon key は「一般社員のIDカード」で、自分の権限の範囲でしか操作できません。
> service_role key は「社長の印鑑」で、何でもできます。
> だから **絶対にブラウザに露出させてはいけない**。サーバーサイドでのみ使います。
>
> **田中**: 怖い…。Webhook で使うのはなぜ？
>
> **AI**: 注文の作成は RLS で「サーバーサイドのみ」に制限しています。
> Webhook は Stripe のサーバーから来るので、通常のユーザーセッションがありません。
> service_role key を使うことで、RLS をバイパスして注文を作成できます。

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | Stripe SDK の導入と、service_role key を使う管理者用 Supabase クライアントを作成 |
| **Why** | 決済処理と、Webhook からの注文作成（RLS バイパス）のために必要 |

## Step 5-1: カート機能（Server Actions）

### 何のためにやったのか

ユーザーが商品をカートに入れたり、数量を変えたり、削除したりする機能を実装した。

### 何をしたのか

Server Actions で 3 つの操作を実装:

| 関数 | 操作 | ポイント |
|------|------|---------|
| `addToCart()` | カートに追加 | 同じバリエーションが既にあれば数量を加算（upsert） |
| `updateCartQuantity()` | 数量変更 | 0 以下になったら自動で削除 |
| `removeFromCart()` | 削除 | user_id チェックで他人のカートを操作できないようにガード |

商品詳細ページの「カートに入れる」ボタンも本実装に変更し、バリエーション選択 UI を追加した。

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: Server Actions って何？API を作るのとどう違うの？
>
> **AI**: Server Actions は「サーバー上で実行される関数」です。
>
> ```
> 従来の API Route:
>   ボタンクリック → fetch("/api/cart", { method: "POST" }) → サーバー処理
>
> Server Action:
>   ボタンクリック → addToCart(variantId) → 直接サーバー処理
> ```
>
> Server Actions は fetch を書かなくていい。関数を呼ぶだけでサーバー処理が実行されます。
> `"use server"` と宣言するだけで、その関数はサーバーで実行されます。
>
> **田中**: えっ、普通の関数みたいに呼べるのにサーバーで動くの？
>
> **AI**: そうです！Next.js が裏側で自動的にネットワーク通信を処理してくれます。
> 開発者から見ると「普通の関数呼び出し」だけど、実際にはサーバーで実行されて結果が返ってくる。
> 魔法のようですが、`"use server"` がその魔法の呪文です。

#### OUTPUT: 田中さんの理解

> **田中のメモ**:
> - Server Actions = `"use server"` を宣言した関数。呼ぶだけでサーバーで実行される
> - `revalidatePath("/cart")` = カートの内容が変わったら、ページを再描画させる命令
> - upsert = 「あれば更新、なければ挿入」。カートに同じ商品を2回追加したら、数量が合算される
> - バリエーション選択 UI: ボタンで 200g / 500g / 1kg を選んでからカートに入れる

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | カートの追加・数量変更・削除を Server Actions で実装した |
| **Why** | ユーザーが商品をカートに入れて買い物を進めるため |
| **How** | `"use server"` で宣言した関数が直接 Supabase の cart_items テーブルを操作する |
| **If** | カートに入れたデータは DB に保存されるので、別のデバイスでも引き継がれる |

## Step 5-3 & 5-4: Stripe Checkout + Webhook + 注文作成

### 何のためにやったのか

「購入する」ボタンを押してから注文が記録されるまでの一連の決済フローを構築した。

### 何をしたのか

#### 決済フロー全体図

```
① カートページで「購入手続きへ」ボタンを押す
  ↓
② /api/checkout（API Route）
  - カートアイテムを取得
  - 在庫チェック
  - Stripe Checkout Session を作成
  - Stripe の決済ページにリダイレクト
  ↓
③ Stripe 決済ページ（外部）
  - ユーザーがカード情報を入力
  - ※ カード情報は自分のサーバーを通らない！
  ↓
④ 決済完了 → 2つのことが起きる
  ├── ユーザー → /checkout/complete（完了ページ）にリダイレクト
  └── Stripe → /api/webhook/stripe に通知（Webhook）
  ↓
⑤ Webhook 処理（/api/webhook/stripe）
  - 署名検証（なりすまし防止）
  - 注文レコード作成（orders テーブル）
  - 注文明細作成（order_items テーブル）
  - 在庫減算（decrement_stock RPC）
  - カートクリア
```

#### 在庫減算の仕組み（楽観的ロック）

```sql
UPDATE product_variants
SET stock = stock - p_quantity
WHERE id = p_variant_id
  AND stock >= p_quantity;  -- ← ここがポイント！
```

`stock >= p_quantity` の条件があるので、在庫が足りなければ更新が行われない。
2人が同時に最後の1個を買おうとしても、先に実行された方だけが成功する。

### 学習の証跡

#### INPUT: AIへの質問

> **田中**: Webhook の署名検証って何？
>
> **AI**: Webhook はインターネット上で「決済が完了しましたよ」という通知を受け取る仕組みです。
> でも問題があります。**誰でもその URL にリクエストを送れてしまう**。
>
> 悪意のある人が偽の「決済完了」通知を送ったら、お金を払わずに注文ができてしまいます。
>
> 署名検証は「この通知が本当に Stripe から来たものか？」を確認する仕組みです。
> Stripe が通知に「秘密の署名」を付けてくれるので、それを検証します。
> 署名が合わなければ偽物と判断して処理を拒否します。
>
> **田中**: 宅配便の「サインください」みたいなもの？
>
> **AI**: 近いですが、もっと厳密です。宅配便は「誰でもサインできる」けど、
> Webhook の署名は「Stripe だけが作れる暗号」です。偽造できません。
>
> **田中**: 配送先が「未設定」になってるのは？
>
> **AI**: 今回の MVP では、決済フローに配送先選択を組み込んでいないためです。
> Chapter 8 で配送先管理を実装した後、決済前に配送先を選択するステップを追加します。
> 今は「決済が正しく動くこと」を優先しています。

#### OUTPUT: 田中さんの理解

> **田中のメモ**:
> - Stripe Checkout = カード情報入力ページは Stripe が用意してくれる。自分のサーバーにカード情報が来ないので安全
> - Webhook = Stripe が「決済完了したよ」と教えてくれる仕組み。ブラウザが閉じても確実に注文が記録される
> - 署名検証 = Webhook が本当に Stripe からのものか確認する仕組み。偽の通知を防ぐ
> - 楽観的ロック = `stock >= p_quantity` の条件で同時購入の在庫問題を解決
> - 注文明細にはスナップショット（購入時点の商品名・価格）を保存。後から価格が変わっても注文記録は当時のまま

#### 鈴木さん（友人エンジニア）のレビュー

> **鈴木**: Webhook のコード見た。署名検証してるのは OK。
> 1点、今は配送先が「未設定」で入ってるけど、本番前に必ず修正が必要だね。
> あと、Webhook は冪等性（同じ通知が2回来ても問題ない設計）を考慮した方がいい。
> stripe_checkout_session_id で重複チェックするとか。
>
> **田中**: 冪等性…メモしておく。鈴木さんに聞いたら「同じ操作を何回やっても結果が変わらないこと」だって。

#### 理解度チェック

| 問い | 田中さんの回答 |
|------|-------------|
| **What** | Stripe Checkout Session 作成、Webhook 処理、注文/注文明細作成、在庫減算、カートクリアを実装 |
| **Why** | 「商品を選んで決済して注文が記録される」一連のフローを完成させるため |
| **How** | カート→Checkout API→Stripe決済→Webhook→注文作成→在庫減算→カートクリア |
| **If** | Webhook がないと、決済はされたのに注文が記録されない事態が起きる。署名検証がないと偽の注文が作られる |
| **Next** | 配送先選択を決済フローに組み込む（Chapter 8）。Webhook の冪等性対応 |
